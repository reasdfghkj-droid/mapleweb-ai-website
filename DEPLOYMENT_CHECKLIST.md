# MapleWeb AI — Phase 4 controlled deployment checklist

This is a **future staging procedure**, not evidence of a deployment. Never run against `main`, any production Worker or the `mapleweb-agent` production D1 database.

1. **GitHub:** inspect and commit the package to `reasdfghkj-droid/mapleweb-ai-website`, branch `mapleweb-ai-agents` **only**, once an authorized write connection is available. The workflow `mapleweb-dev-tests.yml` runs only tests and has `contents:read`.
2. **Cloudflare:** confirm the approved **separate staging** Worker `mapleweb-ai-agents-staging`, staging-only account and the D1 database `mapleweb-agent-staging`. Do not overwrite any existing Worker or production project. Verify Cloudflare pricing/free limits before proceeding; no paid service has been authorized.
3. **Schema migration:** create the `submissions` and `submission_rate_limits` tables in the **staging D1 database only** using `workers/schema.sql`. Use migration review and backups before applying to an existing database; `CREATE TABLE IF NOT EXISTS` alone does not guarantee compatibility with pre-existing schemas.
4. **Variables and secrets:** configure the staging worker's D1 binding as `DB`. Add secrets `TURNSTILE_SECRET`, `RATE_LIMIT_SECRET` (32+ random characters) and `MANAGER_TOKEN` (32+ random characters) via Cloudflare's secret settings only. Set `SITE_ORIGIN` to exactly the staging HTTPS origin with no trailing slash and `TURNSTILE_SITE_KEY` to the public challenge key. Do not put secrets in GitHub, commands, screenshots or chat.
5. **Turnstile action/hostname check:** the client must render Turnstile with `action: 'mapleweb_submit'`; the backend strictly compares the Siteverify `hostname` to the `SITE_ORIGIN` hostname and the Siteverify `action` to `mapleweb_submit`. Use a Turnstile key authorized for this exact staging hostname. Test with a real synthetic token before enabling customer intake.
6. **Fail-closed default:** `SUBMISSIONS_APPROVED=false`; `RETENTION_DAYS=30` is just an unapproved staging proposal. Privacy notice, customer contact and a retention policy require owner review before turning on real submissions.
7. **Deploy staging only:** use the checked `workers/wrangler.staging.jsonc`, not a production config. `node scripts/staging-preflight.mjs` must pass before any deployment. Never change DNS, `main`, the production website Worker or customer sites.
8. **Smoke and end-to-end testing:** `node scripts/smoke-staging.mjs https://STAGING-NAME.workers.dev`. This deliberately expects submissions to be disabled and Manager anonymous access to be denied. For integration testing, use a synthetic request and a valid **test** Turnstile token after approval, verify D1 row and delete it; never test with real customer information.
9. **Manager data deletion:** after owner approval, use `DELETE /api/manager/submissions/{uuid}` with bearer auth and `X-Confirm-Delete: DELETE_THIS_SUBMISSION` for a single reference; use `POST /api/manager/prune` with `{"confirm":"DELETE_EXPIRED_SUBMISSIONS"}` to delete expired rows. Both are destructive and manual; review first. The manager **cannot publish**.
10. **Release gates:** explicit business owner approval, valid privacy policy, customer-approved final version, owner-approved final version, security checks, secure delivery confirmed, real mobile testing and cost confirmation. Publishing is not part of this staging package.

Do not report live availability until the staging URL has been opened and independently checked. The design uses **fixed templates and rules**, not a connected AI model.
